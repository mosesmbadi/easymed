# Demo data

What a fresh EasyMed database contains, how to log in to look at it, and how it
is made.

Every local run starts from an empty database, so this is the first thing
anyone sees of the system. It is generated by `python manage.py
generate_dummy_data`, which `backend/entrypoint.sh` runs after `migrate`
unless `GENERATE_DEMO_DATA` is set to something other than true. The demo,
production and cloud compose files skip the entrypoint, so none of this —
including the known passwords below — reaches a deployment.

## What you will find

Sixty days of a working clinic, busier on weekdays and quiet at weekends —
roughly 250 visits.

| Area | What is there |
| --- | --- |
| **Reception** | Every visit registered, with its consultation billed at the desk |
| **Triage** | Vitals for every visit, fitting the complaint — febrile for malaria, raised blood pressure for hypertension, low SpO2 for pneumonia. A few AI-triage results |
| **Doctor's desk** | A consultation note, signs, diagnosis and plan per visit; referrals out where the case calls for one |
| **Laboratory** | Requests across CBC, Kidney, Liver, Lipid, Thyroid, Electrolytes, Glucose, Urinalysis, Malaria and COVID — collected, resulted with values that fit the diagnosis, approved, and turnaround times you can report on |
| **Sample archive** | Samples archived, some disposed of once past their keeping time, some left expired, some re-tested off the stored sample, some released to a reference lab |
| **Pharmacy** | Prescriptions with dose, frequency and duration, dispensed and billed — injections carrying their syringe and swab |
| **Wards** | Admissions for the sickest cases, observation rounds twice a day, drugs charted on schedule, repeat labs, discharges — and a few patients still on the ward today |
| **Billing** | Invoices in every state: paid at the till or by M-Pesa, part-paid, a few left owing; insured lines split between insurer and co-pay |
| **Insurance** | Five insurers with agreed prices. Claims settled weekly, some short-paid, the last fortnight still outstanding |
| **Finance** | A chart of accounts — till, M-Pesa, collections and supplier-payments accounts — with every receipt posted to one |
| **Procurement** | Weekly reorders from pharmacy and lab: requisition, two approvals, purchase orders per supplier, deliveries (some in two parts), supplier invoices, payments three weeks later |
| **Stock** | A full ledger: receipts, sales, lab consumption, collection draws, transfers to the lab, breakages, two posted stock takes with small shortages and one in progress |
| **Reports** | Gross margin, stock movement, sales and turnaround reports all have history to show |
| **Other** | Announcements with comments, bookings and lab requests from the public site, prescription requests, drug feedback, corporate quotations |

A price rise part-way through the period (amoxicillin, paracetamol,
omeprazole) shows the frozen invoice prices at work: lines billed before it
keep the old price.

### Today looks like a day in progress

Visits keep arriving through today until the moment the demo is generated,
and each stops wherever it would be by then. So the reception, triage, doctor,
lab, pharmacy and billing queues all have patients in them, and the wards have
patients whose discharge is not due yet. Nothing is ever dated in the future.

## How it is made

`customuser/management/utils/demo_activity.py` does it in two parts.

**A demo clock.** `DemoClock` replaces what the backend reads as "now" while
the demo is generated — every `timezone.now()`, every `default=timezone.now`,
Django's own `auto_now_add`, and the few places that stamp reference numbers
from `datetime.now()`. The catalogue, opening stock and prices are dated the
morning before the history begins; each simulated step moves the clock to its
own time. Celery tasks run inline for the duration, on the same clock.

**A discrete-event simulation.** Each visit, admission, reorder, settlement
and housekeeping job is a small script that yields the time of its next step.
`run_scripts` runs every step across all of them in time order, each in its
own transaction. Steps due after the real wall clock are dropped, which is
what leaves today in progress.

Every step goes through the real code: the billing check, the stock signals,
the payment-allocation view the cashier's screen calls, and the purchase-order
and goods-receipt serializers the procurement screens call. A step those rules
refuse is rolled back and printed in red at the end of the run, never forced
in — so a clean run is also evidence those paths work.

The random choices are seeded (`DEMO_SEED`), so every fresh database gets the
same history, relative to the day it is generated.

### Adding to it

Write a script — a generator that yields a time, does one step's work, and
yields the next time — and add it to the list in `seed_demo_world`. Go through
the same service, serializer or view the screen uses rather than creating rows
directly, or the demo stops being evidence that anything works.

## Regenerating

Remove the database volume and start the stack again:

```bash
docker compose -f docker-compose-local.yml down
docker volume rm <project>_postgres_data
docker compose -f docker-compose-local.yml up -d
docker logs -f easymed-backend      # the generator reports as it goes
```

The first start takes about four minutes longer than usual while the history
is simulated. The generator runs before `runserver`, so the API does not
answer until the log shows "Starting development server". Don't restart or
rebuild the stack during that time: the generator is killed partway through,
and the next start finds a half-written history and keeps it. Every step of
the generator skips itself when its data already exists, so restarting
against an existing database changes nothing. If the history stops short of
today, reset the volume again.
